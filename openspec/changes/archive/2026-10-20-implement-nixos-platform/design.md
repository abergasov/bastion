# Design

## Context

См. [proposal.md](proposal.md). Репозиторий greenfield: в нём нет Nix-кода,
flake lock, Make-целей, Nix evaluation или результатов проверок. Существующий
baseline задаёт результат, но не выбранные версии и параметры upstream.

Эта работа должна дать общую NixOS-основу для первого x86_64-хоста с
baseline-поддержкой Hetzner на первом этапе. Политика SSH и fail2ban, серверы VPN, их ключи и состояние,
управление устройствами и ssh_notify принадлежат changes 2–5. Поэтому базовая
конфигурация не должна подменять их временными сервисами или считать себя
готовой к live installation.

## Goals / Non-Goals

**Goals:**

- Дать минимальную структуру `flake.nix`/`flake.lock`, host-конфигурации,
  `disko` и локального Make-интерфейса, которую расширят зависимые changes.
- Хранить относящиеся к провайдеру параметры изолированно от общих NixOS
  модулей; в локальном входе хранить конкретные IPv4/IPv6 и отпечаток SSH
  исходного хоста, не добавляя Hetzner API.
- Использовать нативные NixOS-механизмы для journal и ротации текстовых логов,
  если такой лог добавит интеграция уведомлений.

**Non-Goals:**

- Не выбирать без перепроверки конкретную версию NixOS/nixpkgs, параметры
  диска, swap, SSH, fail2ban, VPN или ssh_notify.
- Не создавать, не шифровать и не передавать секреты, ключи, профили либо
  состояние членства; это работа changes 2–5.
- Не определять процедуру обновления, удалённую сборку, проверку VPS или live
  deployment: это интеграционная работа после foundation, а update workflow
  принадлежит `implement-recovery-and-updates`.

## Decisions

### Единая flake-точка и минимум модулей

`flake.nix` объявит pinned inputs для NixOS, `disko` и `nixos-anywhere`, а
`flake.lock` зафиксирует их. Первый host output соберёт общий platform-модуль и
отдельный host-модуль. В реализации до фиксации lock проверяются latest stable
release, соответствующая ветка nixpkgs и совместимость inputs по официальным
источникам; текущие номера версий в этот план не вносятся.

Это оставляет декларацию сервера в одном стандартном NixOS пути и не добавляет
собственный оркестратор. Альтернатива с отдельными shell-скриптами для сборки и
сети отвергнута: она дублирует NixOS и затрудняет воспроизводимость.

### Разделение общего host и локальных параметров

Общие параметры платформы, provider-specific boot/disk/network-настройки и
конкретные локальные входы будут разнесены по простым Nix-файлам. Реализация
добавит игнорируемый локальный файл с IPv4, IPv6 и ожидаемым SSH host key и
закоммиченный шаблон без реальных значений. Make target читает только эти
значения и приватный SSH-ключ владельца из его обычного SSH-окружения; ключ не
копируется на VPS и не передаётся аргументом Make.

Отдельный локальный вход сохраняет публичные, но зависящие от созданного VPS
значения вне общего baseline. Альтернатива с Hetzner API отвергнута требованиями;
встроенные IP в общий модуль сделали бы первый host менее переносимым.

### Установка с проверкой до disk operations

Make target выполняет только локальную оркестрацию: перед вызовом
`nixos-anywhere` сверяет заданный ожидаемый host key с полученным ключом SSH и
проверяет, что исходная ОС допускает требуемое привилегированное подключение.
После успешных проверок он передаёт выбранную host-конфигурацию
`nixos-anywhere`, который применяет `disko`. Ошибки проверки прекращают
операцию до форматирования.

Прямая ручная последовательность команд не выбрана, поскольку она не даёт
требуемой локальной точки входа и облегчает пропуск предохранительных проверок.
Выбор точной команды, способа проверки privilege и схемы разделов остаётся
проверяемой implementation detail: они зависят от актуальных версий и
документации.

### Логи и ресурсы — нативно, без дополнительного сервиса

Общий модуль задаёт 30-дневное удержание system journal. Если change уведомлений
добавит текстовый auth-log, он подключит его к тому же 30-дневному lifecycle
через стандартную ротацию; platform change не создаёт такой лог заранее.
Документация foundation задаёт форму для записи памяти, свободного диска,
throughput и непроверенных пределов на целевом классе; swap документируется
только если он реально требуется. Полный manual-update workflow, включая
on-VPS build и activation, определяет `implement-recovery-and-updates`.

Не добавляются внешняя система логирования, сборщик метрик или remote builder:
они не требуются baseline и не подходят ресурсу VPS.

### Границы интеграции и порядок готовности

Platform change завершается после собственных проверок flake, host, `disko`,
installer safety и log retention. Он предоставляет foundation changes 2–5;
они не являются его prerequisites. Полный host и live installation — отдельный
интеграционный gate после их завершения, а
`implement-recovery-and-updates` добавляет update/recovery evidence. Поэтому
нет цикла: platform → changes 2–5 → внешний интеграционный gate.

## Risks / Trade-offs

- [Неподходящая схема диска или privilege-проверка может уничтожить VPS] →
  сверять актуальную документацию `disko` и `nixos-anywhere`, требовать точный
  host key и прекращать работу до destructive operation.
- [2 GB RAM или 20 GB могут оказаться недостаточными для сборки/обновления] →
  измерить на VPS, задокументировать headroom и swap; не скрывать проблему
  external builder.
- [Непроверенные upstream версии могут иметь другой интерфейс] → зафиксировать
  версии только после проверки официальных источников и покрыть выбранный путь
  `nix flake check` и build.
- [Частично готовый фундамент могут ошибочно развернуть] → документация
  отделяет готовность foundation от отдельного integration/deployment gate и
  требует завершить changes 2–5 перед запуском установки.
- [Текстовые логи для ssh_notify появятся позже] → не предполагать их формат;
  change 5 проверит формат и добавит ротацию, сохранив заданный срок хранения.

## Migration Plan

1. Реализовать и локально проверить flake, host, disko, Make target и retention
   без доступа к VPS.
2. Передать готовый foundation changes 2–5; их объединение и полный host build
   происходят в отдельном интеграционном gate и не блокируют закрытие этого
   change.
3. После отдельного разрешения на live deployment создать VPS вручную,
   заполнить локальные IPv4/IPv6 и host-key входы, проверить источник SSH и
   привилегии, затем запустить Make target.
4. `implement-recovery-and-updates` определяет безопасное обновление и
   rollback/recreation evidence; при потере административного доступа baseline
   использует recreation, а не неописанный rollback диска.
