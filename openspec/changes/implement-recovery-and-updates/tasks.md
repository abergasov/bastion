# Tasks

## 1. Описать ручное обслуживание

- [ ] 1.1 После готовности `implement-ubuntu-platform` добавить операторскую процедуру weekly и critical update, повторно использующую его native commands: review package/dependency changes, syntax/lint и isolated checks, Ansible update/apply, сохранение SSH-сессии, fresh SSH и оба VPN; проверить platform evidence и failure fixture, что failed update сообщает partial changes и recovery steps без ложного успеха (требование: [ручные обновления](../../specs/server-platform/spec.md#requirement-manual-package-and-configuration-updates)).
- [ ] 1.2 Добавить в ту же процедуру ручной reboot только при необходимости и post-reboot SSH/VPN checks; проверить документационным review и evidence platform suite, что reboot не запускается unattended и failure отмечается без ложного readiness (требования: [ручные обновления](../../specs/server-platform/spec.md#requirement-manual-package-and-configuration-updates), [safe rollout](../../specs/recovery-and-verification/spec.md#requirement-safe-rollout-within-authorized-scope)).
- [ ] 1.3 Реализовать безопасное поддерживаемое повторное применение прежней конфигурации через существующий platform workflow, без гарантии package downgrade и без замены runtime membership; проверить Ubuntu VM test, что восстановление конфигурации не возвращает revoked WireGuard peer или OpenVPN client (требования: [revocations survive lifecycle](../../specs/device-lifecycle/spec.md#requirement-revocations-survive-system-lifecycle-operations), [automation and integration verification](../../specs/recovery-and-verification/spec.md#requirement-automation-and-integration-verification)).

## 2. Реализовать recovery без второй authority

- [ ] 2.1 Добавить operator runbook для обычной потери VPS или административного доступа, который повторно использует installation workflow platform change, verified new host key и existing secret/lifecycle contracts; проверить документационным review, что он не требует console/rescue access или старый VPN server key (требование: [recovery through recreation](../../specs/recovery-and-verification/spec.md#requirement-recovery-through-server-recreation)).
- [ ] 2.2 Встроить в recreation новый локально выпущенный OpenVPN server key/certificate, новый VPS age recipient через существующий SOPS workflow и replacement profiles с единственным новым `peer-fingerprint`; проверить integration fixture, что прежний fingerprint и OpenVPN identity не публикуются, а сохранение WireGuard server key возможно только для non-compromise path (требования: [recovery through recreation](../../specs/recovery-and-verification/spec.md#requirement-recovery-through-server-recreation), [encrypted server VPN keys](../../specs/recovery-and-verification/spec.md#requirement-encrypted-server-vpn-keys-in-git)).
- [ ] 2.3 Добавить recovery preflight, который перед публикацией состояния получает current authoritative revocations от lifecycle contract; при их отсутствии требует fresh trust material и explicit re-enrollment; проверить Ubuntu VM/integration test со stale configuration и старым ciphertext, что revoked credentials остаются denied (требования: [owner-only state](../../specs/recovery-and-verification/spec.md#requirement-owner-only-age-encryption-of-local-credential-state), [revocations survive lifecycle](../../specs/device-lifecycle/spec.md#requirement-revocations-survive-system-lifecycle-operations)).
- [ ] 2.4 Добавить обработку потери owner age key вместе с decrypted local state: создать новую owner identity, fresh credentials и replacement profiles без попытки расшифровать GitHub ciphertext; проверить isolated fixture, что VPS recipient не может прочесть owner-only state и прежние credentials не получают access (требование: [owner-only state](../../specs/recovery-and-verification/spec.md#requirement-owner-only-age-encryption-of-local-credential-state)).

## 3. Обработать подтверждённую компрометацию

- [ ] 3.1 Добавить отдельную compromise procedure, которая пересоздаёт VPS, заменяет его age identity, локально отзывает exposed OpenVPN server certificate и вызывает rotation всех host-accessible server VPN, account-password и ssh_notify secrets; проверить Ubuntu VM/integration scenario, что одна замена recipient не считается recovery и plaintext не попадает в args/logs (требования: [recovery after host compromise](../../specs/recovery-and-verification/spec.md#requirement-recovery-after-host-compromise), [persistent credential state](../../specs/recovery-and-verification/spec.md#requirement-persistent-credential-state-and-protected-secrets)).
- [ ] 3.2 Документировать и проверить ветвление exposure: local CA/client keys сохраняются при VPS-only compromise и заменяются только при подтверждённом local exposure; проверить тестовую матрицу, что replacement profiles pin only new server certificate в обеих ветвях (требования: [recovery after host compromise](../../specs/recovery-and-verification/spec.md#requirement-recovery-after-host-compromise), [OpenVPN profile fingerprint](../../specs/vpn-connectivity/spec.md#requirement-openvpn-profile-server-fingerprint)).
- [ ] 3.3 Добавить явные operator responsibilities для импорта replacement profile, удаления старого auto-connect, disconnect старых sessions и проверки identity в выбранном приложении; проверить review документации, что это не заявлено как автоматизация или обязательная per-device acceptance check (требования: [recovery through recreation](../../specs/recovery-and-verification/spec.md#requirement-recovery-through-server-recreation), [user-owned applications](../../specs/vpn-connectivity/spec.md#requirement-user-owned-applications-and-device-configuration)).

## 4. Завершить обязательное автоматизированное cross-component evidence

- [ ] 4.1 После готовности changes 1–5 переиспользовать их component-suite evidence для platform, secrets, VPN, lifecycle и notifications; добавить только cross-component Ubuntu VM/integration scenario recovery с protocol-compatible test peers и проверить initial/repeated Ansible apply и Ubuntu VM suite (требования: [automation and integration verification](../../specs/recovery-and-verification/spec.md#requirement-automation-and-integration-verification), [server connectivity verification](../../specs/recovery-and-verification/spec.md#requirement-server-connectivity-and-live-operation-verification)).
- [ ] 4.2 Расширить только cross-component scenario позитивными и негативными recovery cases: reboot/reapply, package updates, supported configuration restore, recreation, missing/invalid/expired CRL, stale restore, recipient separation и partial failure между local/server state; проверить, что каждый case сохраняет denied state revoked identity либо сообщает partial failure без success (требования: [automation and integration verification](../../specs/recovery-and-verification/spec.md#requirement-automation-and-integration-verification), [effective OpenVPN revocation](../../specs/device-lifecycle/spec.md#requirement-effective-openvpn-revocation), [authenticated and consistent mutations](../../specs/device-lifecycle/spec.md#requirement-authenticated-and-consistent-mutations)).
- [ ] 4.3 Выполнить formatter, relevant static checks, `ansible-playbook --syntax-check`, `ansible-lint` и initial/repeated apply после integration changes; сохранить результаты отдельно от live evidence и явно перечислить exclusions/unrun checks (требование: [automation and integration verification](../../specs/recovery-and-verification/spec.md#requirement-automation-and-integration-verification)).

## 5. Проверить live readiness после отдельной авторизации

Пункт 5.1 обязателен перед объявлением сервера готовым; готовность кода и
автоматизированных проверок из раздела 4 сама по себе его не заменяет.
Пункт 5.2 — необязательное разрушительное упражнение, а не условие готовности.

- [ ] 5.1 После отдельной явной авторизации выполнить live update/reboot на VPS resource class и записать package-update evidence, memory, disk headroom, throughput, swap, fresh SSH, оба VPN endpoint, IPv4/IPv6 forwarding, IPv6 preference и IPv4 fallback, оба DNS через оба VPN, isolation, OpenVPN performance, log rotation, notification service restart и actual reboot notification; не заявлять о поведении пользовательских приложений (требования: [small VPS resource target](../../specs/server-platform/spec.md#requirement-small-vps-resource-target), [server connectivity verification](../../specs/recovery-and-verification/spec.md#requirement-server-connectivity-and-live-operation-verification)).
- [ ] 5.2 После отдельной явной авторизации при необходимости выполнить live recreation и отдельно согласованный destructive compromise exercise без реальных секретов в logs/arguments; зафиксировать SOPS recipient replacement, rotation evidence и current profile fingerprints. Это optional exercise, а не новый blocker readiness: required recovery evidence остаётся в разделе 4 (требования: [recovery through recreation](../../specs/recovery-and-verification/spec.md#requirement-recovery-through-server-recreation), [recovery after host compromise](../../specs/recovery-and-verification/spec.md#requirement-recovery-after-host-compromise), [safe rollout](../../specs/recovery-and-verification/spec.md#requirement-safe-rollout-within-authorized-scope)).
