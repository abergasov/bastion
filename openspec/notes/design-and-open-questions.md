# Design proposals and open questions

Transferred from AGENTS.md on 2026-10-19. This document is non-normative: proposals are not approved decisions. Where the original discussion repeats a confirmed constraint, the normative requirement lives in [the specifications](../README.md). Resolve choices with the owner before implementing the affected behavior.

## Confirmed decisions — 2026-10-19

- Superseding the earlier VPS-local CA proposal: the administrator's computer generates and retains the OpenVPN CA, all VPN server and client keypairs, issuance records and authoritative device enrollment/revocation records. Client profiles and CRLs are created locally. Client private keys are retained locally for re-export and transferred only to the intended devices, never to the VPS. The VPS receives public verification/access data (CA certificate, signed certificates as needed, CRL, WireGuard public keys, addresses and device metadata) and keeps the deployed access state in protected persistent runtime files outside Git, `/nix/store` and NixOS system generations. NixOS configures services/networking without a competing membership list. See [device-lifecycle](../specs/device-lifecycle/spec.md).
- OpenVPN and WireGuard server private keys are stored in Git as SOPS ciphertext using age, with independent owner and VPS recipients. The owner's private age key and protected backup stay off the VPS; the VPS has its own private age key. Neither private age key belongs in Git or `/nix/store`. sops-nix decrypts server VPN keys into protected `/run/secrets` files at activation. On ordinary VPS replacement, the owner uses their key to replace the VPS recipient with `sops updatekeys` and commits the updated ciphertext; the server VPN keys need not change just because the recipient changes. See [recovery-and-verification](../specs/recovery-and-verification/spec.md).
- The server VPN private keys are the necessary exception to public-only deployment: VPN services need their own private keys. The CA and client private keys are never included in SOPS secrets decryptable by the VPS. If encrypted copies are kept, their recipients exclude the VPS and every identity available on it.
- Root compromise permits arbitrary changes to server admission rules, WireGuard membership and access to server secrets. Keeping CA/client private keys off the VPS protects them and prevents signing with the owner's CA using VPS access alone; it cannot prevent an attacker from accepting arbitrary connections on the compromised host. Recovery recreates the VPS, replaces its age identity and exposed secrets, revokes the old OpenVPN server certificate locally, and updates client trust to reject the old server identity. Local CA/client keys need replacement if exposed, not automatically for VPS compromise alone. Recipient removal does not revoke access to historical ciphertext.
- OpenVPN revocation deploys the updated CRL and briefly restarts OpenVPN. Interruption of all other OpenVPN connections is accepted; service recovery and rejection of the revoked client must be verified.
- This is a personal service; preserving existing client access across server recreation is not required. VPS loss alone does not destroy locally stored CA/client keys. Recovery can issue fresh credentials and replacement profiles if local state is lost. Retained encrypted server VPN keys alone do not restore CA or membership state. This does not remove persistence or revocation requirements during ordinary reboots/rebuilds. See the normative device-lifecycle and recovery-and-verification specifications.

## Proposed design — awaiting discussion

- Pin a supported stable NixOS/nixpkgs revision with a flake lock; pin ssh_notify source. The official download page listed NixOS 26.05 on the analysis date. Verify support again at implementation time and define an update/reboot schedule.
- Begin with small native modules for host configuration, administrative access/firewall, WireGuard, OpenVPN, and notifications. Avoid containers, a web administration panel, and orchestration frameworks unless a concrete requirement calls for them.
- Retain `admin`; use SSH keys only, explicitly disable password and keyboard-interactive SSH authentication, and prohibit root SSH login. Recommend a unique admin sudo password per host. Root account policy remains open, but console recovery and an emergency root password are not required under the agreed server-recreation policy.
- Keep public key-only SSH as confirmed above. Propose the native NixOS fail2ban SSH jail using the systemd journal and the selected firewall backend. Initial policy proposal: 5 matching failures within 10 minutes, a 1-hour ban, increasing on repeat offenses up to 24 hours. Scope bans to SSH ports, support IPv4 and IPv6, and provide status/unban instructions. Do not blanket-exempt VPN or private subnets. Verify actual log matching and ban/unban behavior. Reference: [NixOS fail2ban](https://wiki.nixos.org/wiki/Fail2ban).
- Default-deny inbound and forwarding rules, allowing public SSH, TCP/443 for OpenVPN, and UDP/443 for WireGuard. Do not open TCP/80, add an HTTPS service, or mark entire VPN interfaces trusted.
- Separate OpenVPN and WireGuard address pools. Propose client isolation within and across VPNs, and block access to provider private/metadata networks unless explicitly needed.
- Full-tunnel routing is confirmed. Route DNS through the VPN to the selected public resolver (`1.1.1.1` or `8.8.8.8`). A server-side forwarder is optional and not yet agreed; if used, expose it only to loopback/VPN. Choose dual-stack tunneling where the provider supports it; otherwise explicitly prevent client IPv6 bypass. Disabling IPv6 on the server alone is insufficient. Client kill-switch behavior and local-network exceptions must be specified and tested per operating system; a server configuration alone cannot enforce them.
- OpenVPN: current AEAD configuration, no compression, server identity verification on clients, and tls-crypt-v2 if supported by all selected clients. Individual device certificates and local CA/key generation are confirmed above. The recovery procedure must define and verify how each selected client rejects a compromised server certificate.
- WireGuard: narrowly scoped allowed addresses. Separate device keypairs generated and retained on the administrator's computer, with public-only peer deployment, are confirmed above.
- Extend the agreed sops-nix/age scheme to Telegram credentials; this remains a proposal. Never interpolate decrypted secrets into Nix expressions or derivations: `/nix/store` is readable by local users.
- Keep operational logs with bounded retention; do not log VPN payloads or DNS query history by default. Telegram receives SSH metadata; agree on notification contents.
- No claim of absolute security: a VPS provider controls the host, and VPNs do not guarantee anonymity or bypass of traffic filtering.

## Remaining credential proposals

- `/var/lib/bastion` is a possible location for deployed public server state; exact paths are implementation details. Optional restores must reconcile current revocations from local authoritative records before exposing VPN listeners.
- Choose protected local storage and optional backup tooling for the CA, issuance records, client private keys and enrollment/revocation records. Local generation and retention are agreed; encrypted repository storage for this local state has not been selected. Any encrypted copies must remain inaccessible to the VPS.

## Questions still open

- Concrete server size, public addresses, and tooling for the agreed automated SSH installation. Architecture, public IPv4/IPv6, IP-only endpoints, UDP/443 for WireGuard, and recreation instead of console/rescue recovery are agreed.
- IPv6 routing inside both VPNs (discussion item 8 remains unanswered), final DNS provider and direct versus forwarded DNS, client-to-client/local-network access, and full-tunnel/kill-switch setup for Android, iOS, Windows, macOS, and Linux. Expected client count and no artificial quotas are agreed.
- Administrator key type (including optional hardware-backed keys), sudo password policy, and root account policy; no console recovery requirement.
- Choose local secret storage/backup tooling and the per-client procedure for rejecting a compromised OpenVPN server identity. Local key generation, CA ownership, private-key retention for re-export, the Makefile interface and single-host scope are agreed.
- Required notification delivery guarantees, update cadence, maintenance windows, and provisioning/recovery of non-VPN secrets. Additional backups of local credential state are optional; choose a destination only if they are wanted. Choose protected storage for the owner's age-key backup.
