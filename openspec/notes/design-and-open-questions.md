# Design proposals and open questions

Transferred from AGENTS.md on 2026-10-19. This document is non-normative: proposals are not approved decisions. Where the original discussion repeats a confirmed constraint, the normative requirement lives in [the specifications](../README.md). Resolve choices with the owner before implementing the affected behavior.

## Confirmed decisions — 2026-10-19

- Target servers have approximately 1 vCPU, 2 GB RAM and 20 GB local disk. This is the resource class for implementation and verification, not a measured minimum or a throughput guarantee. The owner's current plan's price and traffic allowance are not portable requirements. Installation, operation and updates must be checked on this resource class; updates are built on the VPS itself and any needed swap must be documented. An external builder is not the selected workflow. See [server-platform](../specs/server-platform/spec.md).
- Initial server setup sets predefined, owner-supplied passwords for `admin` and `root`, following the existing Ansible setup's account-password model. Only `admin` may log in over SSH, using an authorized key; direct SSH login as `root` or any other account is forbidden even with a valid key. To become `root`, the administrator runs `su` after logging in as `admin` and authenticates with the `root` password. This also governs privilege elevation for device management commands. Account passwords do not enable SSH password authentication or introduce a console-recovery dependency. Account-password material is stored in Git as SOPS/age ciphertext for the owner and VPS and provisioned through sops-nix protected runtime files during installation and recreation. Actual password values are not copied into documentation. See [server-administration](../specs/server-administration/spec.md).
- fail2ban protects public SSH using the default SSH jail policy supplied by the selected, pinned NixOS/nixpkgs revision and its fail2ban package. Do not customize failure thresholds, observation windows, ban durations, repeat-offender escalation or exemptions. This replaces the earlier proposal for 5 failures in 10 minutes and escalating bans from 1 to 24 hours. Enabling SSH protection, integrating actual logs/firewall, and verifying matching and ban/unban on IPv4 and IPv6 remain required. Record the effective defaults during implementation. See [server-administration](../specs/server-administration/spec.md).
- Both OpenVPN and WireGuard provide server-side IPv4/IPv6 internet forwarding. The VPS isolates clients within and across both VPNs, including devices belonging to the same user. The 2026-10-20 scope decision below supersedes earlier requirements for Bastion to configure and verify client kill switches, local-network blocking and routing on five operating systems. Those device-side behaviors are the user's responsibility. See [vpn-connectivity](../specs/vpn-connectivity/spec.md).
- Server-advertised settings and generated profiles list public DNS resolvers Cloudflare `1.1.1.1` first and Google `8.8.8.8` second. Both are reachable through the VPN tunnel and VPS internet connection; no separate DNS service or forwarder is deployed on the VPS for clients. Actual resolver selection, failover and enforcement on the device are the user's responsibility. List order does not guarantee exclusive Cloudflare use or immediate return after recovery. See [vpn-connectivity](../specs/vpn-connectivity/spec.md).
- Superseding the earlier VPS-local CA proposal: the administrator's computer generates and retains the OpenVPN CA, all VPN server and client keypairs, issuance records and authoritative device enrollment/revocation records. Client profiles and CRLs are created locally. Client private keys are retained locally for re-export and transferred only to the intended devices, never to the VPS. The VPS receives public verification/access data (CA certificate, signed certificates as needed, CRL, WireGuard public keys, addresses and device metadata) and keeps the deployed access state in protected persistent runtime files outside Git, `/nix/store` and NixOS system generations. NixOS configures services/networking without a competing membership list. See [device-lifecycle](../specs/device-lifecycle/spec.md).
- OpenVPN and WireGuard server private keys are stored in Git as SOPS ciphertext using age, with independent owner and VPS recipients. The owner's private age key stays off the VPS; the VPS has its own private age key. Neither private age key belongs in Git or `/nix/store`. sops-nix decrypts server VPN keys into protected `/run/secrets` files at activation. On ordinary VPS replacement, the owner uses their key to replace the VPS recipient with `sops updatekeys` and commits the updated ciphertext; the WireGuard server key may be retained if unexposed, but every VPS recreation uses a fresh locally generated OpenVPN server key and certificate, with the private key encrypted for the new SOPS recipients. See [recovery-and-verification](../specs/recovery-and-verification/spec.md).
- Local CA/client private keys, issuance records and authoritative enrollment/revocation records are stored in Git as age-encrypted files for the owner only. The owner's private age key is kept in KeePassXC, outside the project repository and off the VPS; decrypted working files stay outside the repository with restrictive permissions. Management operations save updated encrypted state before reporting success, without requiring automatic commits or pushes. Server VPN keys retain the separate SOPS/sops-nix scheme with owner and VPS recipients. The 2026-10-20 decision below supersedes the earlier requirement for an independent backup of the owner's age key. See [recovery-and-verification](../specs/recovery-and-verification/spec.md).
- The server VPN private keys are the necessary exception to public-only deployment: VPN services need their own private keys. The CA and client private keys are never included in SOPS secrets decryptable by the VPS. Their age-encrypted repository copies exclude the VPS and every identity available on it.
- Root compromise permits arbitrary changes to server admission rules, WireGuard membership and access to server secrets. Keeping CA/client private keys off the VPS protects them and prevents signing with the owner's CA using VPS access alone; it cannot prevent an attacker from accepting arbitrary connections on the compromised host. Recovery recreates the VPS, replaces its age identity and exposed secrets, revokes the old OpenVPN server certificate locally, and generates replacement profiles pinning the new server identity. Users are responsible for updating trust in their applications. Local CA/client keys need replacement if exposed, not automatically for VPS compromise alone. Recipient removal does not revoke access to historical ciphertext.
- Each initial server creation and VPS recreation uses a new OpenVPN server key and certificate generated on the administrator's computer. Generated `.ovpn` profiles pin exactly that certificate's SHA-256 fingerprint using `peer-fingerprint`; no separate hash file is needed. Bastion provides replacement profiles after recreation. Importing them, removing old profiles and automatic connection entries, disconnecting old sessions and verifying the server in the chosen application are the user's responsibility. Recreation and local revocation do not update application trust automatically. Routine reboots and NixOS rebuilds preserve the current identity. Generated profiles retain the pin; per-application compatibility and enforcement are outside Bastion acceptance criteria. See [vpn-connectivity](../specs/vpn-connectivity/spec.md) and [recovery-and-verification](../specs/recovery-and-verification/spec.md).
- OpenVPN revocation deploys the updated CRL and briefly restarts OpenVPN. Interruption of all other OpenVPN connections is accepted; service recovery and rejection of the revoked client must be verified.
- This is a personal service; preserving existing client access across server recreation is not required. VPS loss alone does not destroy locally stored CA/client keys. Recovery can issue fresh credentials and replacement profiles if local state is lost. Retained encrypted server VPN keys alone do not restore CA or membership state. This does not remove persistence or revocation requirements during ordinary reboots/rebuilds. See the normative device-lifecycle and recovery-and-verification specifications.

- Installation uses `nixos-anywhere` and `disko` over SSH. The owner's existing Ed25519 public key is already registered for new VPS creation, providing initial access for the owner or script. The installer must verify the target host's identity and sufficient privileges in the source OS before disk operations; installed Bastion continues to allow only `admin` over SSH with elevation through password-authenticated `su`. Concrete IPv4/IPv6 addresses are per-host inputs. See [server-platform](../specs/server-platform/spec.md) and [server-administration](../specs/server-administration/spec.md).
- Updates are manual: update dependencies in `flake.lock`, check and build on the VPS, apply, then verify fresh SSH access and both VPNs. Routine maintenance uses a weekly window, with out-of-schedule critical security fixes. Reboots are manual when required, followed by connectivity checks; the exact weekly day/time is an operational choice. See [server-platform](../specs/server-platform/spec.md).

- If integration checks demonstrate an unsupported NixOS log format, a targeted patch to `ssh_notify` is authorized to provide compatibility. The patch must have a focused regression test and be included reproducibly in the pinned Nix package; compatibility remains to be verified. The 2026-10-20 decisions below define notification scope and delivery retries. See [ssh-notifications](../specs/ssh-notifications/spec.md).

- The entire ssh_notify application configuration, including Telegram credentials and all other configuration values, is stored in Git as SOPS/age ciphertext using the same owner and VPS recipients as account-password secrets. Deployment and recovery use this encrypted configuration directly; sops-nix supplies a protected runtime configuration file under `/run/secrets` for the service. Plaintext stays out of Git, Nix expressions, `/nix/store`, logs and command arguments. VPS replacement updates the recipient; host compromise additionally requires rotation of exposed credentials. Notification scope and delivery retries are defined by the 2026-10-20 decisions below. See [ssh-notifications](../specs/ssh-notifications/spec.md) and [recovery-and-verification](../specs/recovery-and-verification/spec.md).

## Confirmed decisions — 2026-10-20

- Bastion configures and verifies the server and generates device credentials/profiles; users may choose any protocol-compatible application and own its configuration and behavior. This supersedes the five-OS application support and device verification requirements. Kill switches, local-network blocking, routing/DNS behavior, profile installation/replacement and server identity verification in applications are user responsibilities. Server-side IPv4/IPv6 forwarding, DNS settings/reachability, peer isolation and revocation remain required. Generated OpenVPN profiles retain `peer-fingerprint`; server/profile tests use protocol-compatible test peers without a mandatory application or OS matrix. Application selection is no longer an open project decision. See [vpn-connectivity](../specs/vpn-connectivity/spec.md) and [recovery-and-verification](../specs/recovery-and-verification/spec.md).

- ssh_notify owns notification generation and Telegram delivery for SSH logins and boots/reboots, including up to five retries after an unsuccessful initial send (six attempts total), stopping on success. Loss after exhaustion is accepted; no durable queue or guaranteed eventual delivery is required. Failures are reported without exposing secrets, and later notifications continue to be processed. A targeted patch is authorized with regression tests and reproducible inclusion in the pinned Nix package. Bastion adds no separate sender, retry wrapper or delivery queue. See [ssh-notifications](../specs/ssh-notifications/spec.md).
- GitHub is sufficient as the remote copy of encrypted VPN credential state; no additional backup system is requested. The owner's private age key remains in KeePassXC, outside Git and off the VPS, with no separate backup. This explicitly supersedes the independent key-backup requirement. The owner accepts that loss of the key and decrypted local state prevents recovery of owner-only encrypted GitHub copies; recovery then requires a new age identity, fresh VPN credentials, explicit enrollment and replacement profiles. Old credentials must not regain access. Only committed and pushed state exists in the GitHub copy; automatic commits/pushes per operation remain unnecessary. See [recovery-and-verification](../specs/recovery-and-verification/spec.md).

- The latest stable NixOS release and corresponding nixpkgs branch are selected when preparing initial installation, verified against official sources and pinned in `flake.lock`. Manual updates remain required. The earlier open release-selection question is resolved. See [server-platform](../specs/server-platform/spec.md).
- Inbound services are limited to SSH, OpenVPN TCP/443 and WireGuard UDP/443. Outbound traffic from the VPS and authenticated VPN clients has no destination/port restrictions, including no special provider-private/metadata denylist. Required network control and return traffic remain permitted. Previously agreed VPN peer isolation still applies; concrete address pools are implementation details. This supersedes the proposal to block provider private/metadata networks. See [vpn-connectivity](../specs/vpn-connectivity/spec.md).
- Use default operational logs and logging levels, retain logs for 30 days, and automatically clean up older logs through native facilities, covering the journal and deployed service log files. Secret-exclusion requirements remain in force. See [server-platform](../specs/server-platform/spec.md).
- OpenVPN prioritizes maximum practical performance on the target VPS without weakening required security or changing TCP/443. Exact ciphers, compression policy, control-channel protection and acceleration are implementation choices to verify against upstream documentation and target-host measurements. No exact cipher or tls-crypt-v2 selection is approved by this performance objective alone. See [vpn-connectivity](../specs/vpn-connectivity/spec.md).
- The owner manually creates an IPv4/IPv6 VPS with their public SSH key, enters its addresses locally and runs a local Make installation target. The private SSH key stays local. Source-OS privileges and host identity are installation checks, not unresolved architecture questions. See [server-platform](../specs/server-platform/spec.md).
- No redesign of existing SSH login notification wording is requested. The earlier open wording question does not imply a defect. Explicit boot/reboot detection remains required and must distinguish system boot from notification-service restart. See [ssh-notifications](../specs/ssh-notifications/spec.md).

## Implementation choices and proposals

These details are not additional owner decisions required before implementation.
Select the smallest native implementation satisfying the specifications; proposals
below do not independently impose requirements.

- Begin with small native modules for host configuration, administrative access/firewall, WireGuard, OpenVPN, and notifications. Avoid containers, a web administration panel, and orchestration frameworks unless a concrete requirement calls for them.
- Explicitly disable keyboard-interactive SSH authentication. Admin-only SSH-key login, prohibiting direct root SSH login, switching to root through `su`, and setting predefined `admin`/`root` passwords at initial setup are agreed. Recovery still uses server recreation without requiring console access.
- Select VPN address pools and firewall rules that implement the agreed inbound/outbound policy and client isolation. Do not mark entire VPN interfaces trusted.
- Select OpenVPN parameters for the agreed performance objective while preserving security; the earlier list of AEAD, no compression and tls-crypt-v2 was a proposal, not an approved parameter set.
- WireGuard: narrowly scoped allowed addresses. Separate device keypairs generated and retained on the administrator's computer, with public-only peer deployment, are confirmed above.
- No claim of absolute security: a VPS provider controls the host, and VPNs do not guarantee anonymity or bypass of traffic filtering.

## Remaining credential proposals

- `/var/lib/bastion` is a possible location for deployed public server state; exact paths are implementation details. Optional restores must reconcile current revocations from local authoritative records before exposing VPN listeners.
- Owner-only age encryption for local credential state in Git and KeePassXC storage of the owner's private age key are agreed. GitHub is the selected remote copy of encrypted state; no additional backup system or separate age-key backup is planned. File layout is an implementation detail.

## Inputs and checks remaining before installation

- Supply concrete public IPv4/IPv6 addresses in local host configuration and verify the source OS's SSH account, installation privileges and host identity for the chosen VPS.
- Verify the current stable NixOS release, upstream compatibility and performance choices during implementation. These are engineering checks, not pending owner policy decisions.
