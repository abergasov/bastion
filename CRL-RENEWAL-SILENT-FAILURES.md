# Автопродление CRL может падать без уведомления

Статус: открыто. Найдено при ревью 2026-11-02, ещё не исправлено.

## Суть

`roles/vpn/files/bastion-vpn-renew-crl` фиксирует сбой и уведомляет о нём через
`trap record_failure ERR`. Обработчик записывает `result: failed` в
`/var/lib/bastion/vpn/crl-status.json` и отправляет сообщение в Telegram через
`ssh_notify message`.

Bash вызывает ERR-trap только для команды, завершившейся с ненулевым кодом.
Явный `exit 1` этот trap не вызывает. Поэтому следующие отказы проходят мимо
`record_failure`:

| Строка | Сообщение | Когда возникает |
|--------|-----------|-----------------|
| 136 | `VPN state changed during CRL renewal; retry` | `current` сменился между проверкой и захватом lock (параллельный publish/revoke) |
| 184 | `renewed CRL is too close to expiry` | новый CRL получился с `nextUpdate` внутри 7-дневного окна (часы, `default_crl_days`) |
| 186 | `renewed CRL sequence is invalid` | номер в подписанном CRL не совпал с ожидаемым |

Кроме того, ошибки внутри process substitution (`read -r ... < <(read_metadata ...)`,
`< <(read_status)`) не передают код возврата в основной shell и тоже не вызывают
ERR. В этих случаях сбой проявится позже и в другом месте, либо не проявится
совсем.

У `bastion-vpn-renew-crl-activate.service` и `bastion-vpn-renew-crl.service`
нет `OnFailure=`. Значит, systemd тоже никого не уведомит.

## Последствия

Таймер `bastion-vpn-renew-crl.timer` — единственный штатный механизм продления
CRL, ручной `make vpn-renew-open` нужен только для восстановления. Если продление
каждый день падает по одной из причин выше:

1. `crl-status.json` продолжает показывать прошлый успешный результат, и уведомление не приходит;
2. CRL (срок жизни 30 дней) истекает;
3. `bastion-vpn-verify-state` без `--allow-expired` отклоняет состояние, а
   `ExecStartPre` у `openvpn-server@bastion` не даёт OpenVPN стартовать при следующем рестарте;
4. OpenVPN недоступен всем клиентам, и узнать об этом можно только от пользователей.

Для одноразового сбоя (строка 136, гонка с publish) это не страшно: следующий
запуск таймера повторит попытку. Опасны устойчивые причины (строки 184, 186),
потому что они будут повторяться каждый день до истечения CRL.

## Как исправить

Минимальное изменение: обрабатывать любой ненулевой выход, а не только ERR.

- Заменить `trap record_failure ERR` на EXIT-trap, который вызывает
  `record_failure` при ненулевом коде (`code=$?; test "$code" -eq 0 || record_failure`).
- Объединить его с существующим `trap 'rm -rf "$work"' EXIT` в строке 156,
  иначе тот перезапишет обработчик. Например: отдельная функция `cleanup`,
  которая удаляет `$work`, если он задан, и вызывает `record_failure` при ошибке.
- Вывод `read_metadata` и `read_status` читать через обычную подстановку
  (`value=$(read_metadata ...)`), чтобы их ошибки доходили до trap.

Дополнительно, на случай если упадёт сам скрипт уведомления: добавить юнитам
продления `OnFailure=` с отдельным oneshot-уведомлением.

## Как проверить

Расширить `tests/server-crl-renewal-test.sh`: для каждой из трёх веток с `exit 1`
проверять, что после неудачного запуска в `crl-status.json` записано
`result == "failed"`, а в `$NOTIFY_LOG` есть сообщение. Например:
- подменить `current` между проверкой и lock;
- задать `default_crl_days` меньше окна;
- подставить неверный `crlnumber`.
